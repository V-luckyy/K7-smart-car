0. 先建立正确模型：这不是一个“从 main 顺着看完”的裸机工程

真正的处理核心是 STM32F407 MCU。MPU6050/ICM20948只是外置IMU传感器。程序结构是“启动代码 → 板级初始化 → FreeRTOS任务 → 中断/任务共同维护全局状态 → 100 Hz电机闭环”。

你首先跟的主线

Reset_Handler → SystemInit() → main() → systemInit() → start_task → 各业务任务。

控制核心

Balance_task每10 ms执行：读编码器、选控制来源、安全检查、逆运动学、PI、写TIM8 PWM。

通信核心

UART/CAN/遥控中断和USB/PS2任务把命令写入共享结构，控制任务再读取；多数路径没有队列快照。

传感器核心

IMU由100 Hz任务轮询；编码器由定时器硬件计数；GY53由EXTI边沿中断+DWT计时。

先分清三套“型号选择”，否则很容易改对代码却烧错固件

① Keil Target（编译期）Akm / Diff / Mec / 4WD / Omni；决定运动学宏和唯一参与链接的CarType参数文件
② PCB硬件版（运行期）V1.0 / V1.1 / V1.2；由IMU ID和版本脚识别，决定CAN、USB、OLED、PS2、RGB等引脚
③ robot.type（运行期机械档）当前Diff固件读取PC2/ADC1_IN12电位器，选择轮距、轮径、减速比、编码器精度和默认PI
当前基线：最近实际构建的是Diff_Car，使用DIFF_CAR和CarType/diff_robot_init.c。但它仍可能运行在V1.0、V1.1或V1.2 PCB上，并由robot.type再选择具体机械参数。DIFF_CAR绝不等于V1.0。
实机调试先做安全隔离：抬起驱动轮或断开电机功率，并让PE4使能输入处于失能状态。当前Keil调试配置没有冻结TIM8；CPU停在断点时，PWM定时器可能继续输出最后的占空比。

入口工程是 USER/WHEELTEC.uvprojx。它有5个Target，同一套公共代码通过宏选择不同运动学；当前目录中最新输出是Diff_Car.hex和OBJ/Diff_Car.map，因此本手册以差速车为主。

Keil初学者最常踩的坑：Project窗口里能看到某个.c，不代表它参与当前Target构建。比如CarType组里列着5个文件，但Diff_Car Target只包含diff_robot_init.c，其余设置为Exclude from Build。修改错文件会“编译成功但行为完全不变”。
工程技术栈：这是µVision 5.34 + ARMCC 5.06u7 + STM32 Standard Peripheral Library工程，不是CubeMX/HAL工程（USB底层局部使用HAL接口）。不要把CubeMX生成的HAL_GPIO_Init或MX_USARTx_UART_Init直接粘进现有初始化链。磁盘中“编译进固件”的驱动也不一定会运行：V1.0/V1.1/V1.2仍由system.c和main.c的运行期分支决定。

每次动手前固定检查

  1. Keil左上角Target下拉框是否是你要烧录的车型。
  2. Options for Target → C/C++ → Define 中是否只有一个车型宏。
  3. 修改的文件是否在当前Target中未被Exclude from Build。
  4. Build后确认生成时间更新的是对应.axf/.hex/.map。
  5. 烧录文件与当前Target一致，不要把旧的Diff_Car.hex误当成刚编译结果。

为什么刚上电电机不响应

0～约1秒：板级初始化和OLED启动画面具体时间还取决于IMU、OLED和USB初始化。
FreeRTOS开始：Time_count以100 Hz递增每10 ms加1，CONTROL_DELAY=1000实际上代表10秒，不是1000 ms。
0～10秒：UART/CAN/APP控制被忽略或尚不执行部分中断仍会读字节，但回调按Time_count提前返回。
10～12秒：低速前进自检Drive_Motor(0.2,0,0)并检查编码器方向/车型。
12～12.3秒：停止并结束自检清零目标，设置check_end。
约12.3秒后：才进入正常控制来源选择这是“串口有数据但车不动”首先要排除的时间窗口。

4. 硬件版本不是Keil Target：它在运行时自动识别

Keil Target决定车型运动学，SysVal.HardWare_Ver决定控制板版本和引脚映射，robot.type决定同一车型内的机械参数档。这三套选择是不同维度。

V1.0

MPU6050 ID = 0x68

  • 经典PS2插座，PE0～PE3
  • CAN1：PA11/PA12
  • 无USB Host
  • 无USART2/D50A
  • 旧OLED映射
  • 旧RGB LED：PD13/14/15
V1.1

ICM20948 ID = 0xEA，版本脚000

  • USB手柄，PA11/PA12
  • CAN1移到PD0/PD1
  • 无USART2/D50A
  • 仍使用旧OLED映射
  • RGB灯带PWM：PB14/PB15/PE6
V1.2

ICM20948 ID = 0xEA，版本脚001

  • 继承V1.1的USB和新CAN
  • USART2：PD5/PD6，连接RS485/D50A
  • OLED因此改到PD7/PD4/PE1/PE0
  • 创建D50A任务

版本脚为PE2、PE3、PC13；ICM20948分支读取三位值，当前只接受0和1，其他组合直接诊断停机。Diff Target随后在CarType/diff_robot_init.c:18–73读取PC2 ADC并把robot.type分到0～5，再填充robot.HardwareParam和默认PI。调试时第一批Watch变量应包含g_system_diag.mpu6050_id、g_system_diag.icm20948_id、g_system_diag.hardware_version_bits、SysVal.HardWare_Ver、robot.type和robot.HardwareParam。

定时器倍频规则：APB预分频不等于1时，挂在该APB上的定时器时钟等于PCLK×2。因此“APB1=42 MHz”不代表TIM2～5也是42 MHz，它们实际是84 MHz。

APB1 Timer84 MHzTIM2/3/4/5编码器、TIM12灯带、TIM4顶配舵机灯带/舵机常见配置：84M / 84 / 10000 = 100 Hz

如果你要改系统主频，必须同时检查这些位置

  1. USER/stm32f4xx.h:123：HSE_VALUE必须等于实物晶振。
  2. USER/system_stm32f4xx.c:316–331：PLLM/N/P/Q。
  3. USER/system_stm32f4xx.c:597–605：AHB、APB1、APB2分频。
  4. USER/system.c:202：当前写死delay_init(168)，主频变更必须改。
  5. FreeRTOSConfig.h：configCPU_CLOCK_HZ=SystemCoreClock，确保变量更新正确。
  6. TIM8电机PWM、TIM1遥控、TIM9/TIM4舵机、TIM9/TIM12灯带的ARR/PSC全部重算。
  7. ADC时钟不得超过器件上限；CAN波特率重新计算；USB分支仍必须得到48 MHz。
  8. GY53按SystemCoreClock/1,000,000换算DWT，SystemCoreClock错误会让距离同比例错误。
当前HSE失败路径存在隐患：HSE失败时可能留在16 MHz HSI，但SystemCoreClock和delay_init(168)仍按168 MHz使用，表现为RTOS、UART、PWM和GY53距离整体异常。遇到“能烧录但所有时序都怪”时先查HSE/PLL，不要先改业务代码。

精确抢占规则

  • NVIC_PriorityGroup_4表示4位全是抢占优先级、0位子优先级；代码写的SubPriority不生效。
  • 同级IRQ不能互相嵌套；同时pending时按异常号较小者先。p3中CAN1_RX0先于UART4；p5中EXTI9_5→TIM1_CC→USART2→OTG_FS。
  • configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5：IRQ 0～4绝不能调用FreeRTOS API；IRQ 5～15只能调用带FromISR后缀的API。
  • FreeRTOS临界区使用BASEPRI=5，只屏蔽p5～15；USART3、CAN、UART4、USART1仍可能打断临界区中的任务代码。
  • 编码器TIM2/3/4/5、电机TIM8和ADC当前不使用中断；它们分别由硬件计数、PWM输出或任务轮询完成。
未启用不等于以后能直接开：CAN2_RX1宏为0；EXTI15_10当前链接到启动文件的弱Default_Handler。若以后只开启中断源而没有把正确Handler加入当前Keil Target，CPU会进入默认死循环。

11. 我想改某功能，到底改哪几个文件

通用变更检查单

  • 先确认Keil Target、硬件版本和真正参与构建的源文件。
  • 查完整引脚表，确认端口、AF、定时器通道、EXTI线和版本复用均不冲突。
  • 初始化函数放在正确阶段：RTOS API相关外设必须在调度器运行后初始化。
  • 中断只采数据/清标志；复杂解析和浮点运算放到任务。
  • 明确数据结构的唯一写者；跨ISR/任务使用volatile、临界区、队列或双缓冲。
  • 新增.c后加入所有需要的Keil Target；确认不是Exclude from Build。
  • 重新计算任务栈、heap、执行周期和CPU占用。
  • 先用Watch验证原始数据，再接入控制；最后才允许电机带负载。
  • Build后检查0 error/0 warning、map文件符号、hex时间，再烧录。

15.3 上电后为什么不是立刻捕获

① systemInit()调用GY53_PWM_Init()。来源：USER/system.c:318
② DWT启动CYCCNT=0，使能CPU周期计数。此时168 MHz意味着每周期约5.952 ns。
③ GPIO/EXTI只配置PE5/7/8为下拉输入，上升沿和下降沿检测都打开。但EXTI IMR仍屏蔽，NVIC也禁用。
④ RTOS创建任务USER/main.c:132创建优先级2、栈128 words的GY53任务。128 words=512 bytes，不是128 bytes。
⑤ 延时300 ms传感器电源和PWM先稳定。GY53_PWM_CAPTURE_DELAY_MS
⑥ 原子式开放先清等待下降沿状态和pending，再设置capture_enabled=1，开放IMR/NVIC。诊断位同时置位。

15.4 一次有效PWM到底经历了什么

1. GY53输出上升沿例如前传感器PE5由0变1。硬件将EXTI5 pending置1。
2. CPU进入EXTI9_5保存现场，执行统一Handler。pwm_irq_count++
3. 锁定来源pending = EXTI->PR & mask，发现EXTI5。随后清该pending位。
4. 读取当前电平PE5仍为1，于是识别为上升沿。代码不是硬件输入捕获寄存器，而是ISR服务时读GPIO。
5. 保存起点rise_cycle[0]=DWT->CYCCNT，wait_fall[0]=1。edge_count++
6. GY53输出下降沿PE5由1变0，再次进入同一个中断。若已经看到上升沿，才配对计算。
7. 无符号周期差now-rise得到高电平占用的CPU周期数。DWT回绕时无符号减法仍成立，单次脉宽远小于25.57 s。
8. 周期换μs除以SystemCoreClock/1,000,000；168 MHz时除以168。last_pulse_us无论有效与否都会更新。
9. 合法区间判断20～40000 μs为有效；否则只增加invalid_count。无效帧不会覆盖上次有效距离。
10. μs换mmdistance_mm=pulse_us/10U，再写high_us/distance_mm/online/updated/update_count。整数除法向下截断，分辨率是1 mm。

完整算例：PWM高电平代表1234 mm

high_us = 1234 × 10 = 12340 μs
DWT周期差 = 12340 × 168 = 2,073,120 cycles
pulse_us = 2,073,120 / 168 = 12,340 μs
distance_mm = 12,340 / 10 = 1,234 mm
distance_m = 1,234 / 1000.0f = 1.234 m
时钟是公式的一部分：如果MCU实际不是168 MHz而SystemCoreClock仍写168 MHz，所有GY53距离会按同一比例整体偏大或偏小。先在Keil Watch确认SystemCoreClock，再怀疑传感器。

15.7 三个传感器能否同时读取

可以。PE5、PE7、PE8各有独立EXTI pending位、上升沿时间和等待下降沿状态。一次进入EXTI9_5后，Handler会按“前→左→右”的顺序把当时所有pending位都处理掉，因此三路无需软件轮询切换。

但“可以同时工作”不等于“每个边沿都有硬件时间戳”：EXTI每条线只有一个pending位，代码在ISR服务时才读取GPIO当前电平。如果同一路在CPU来不及处理时已经发生两次变化，pending不能排成两条消息；USART3优先级0、CAN/UART4优先级3、USART1优先级4又都可以抢占优先级5的GY53中断，过长ISR会产生抖动或漏边沿。需要更强鲁棒性时，应把三路改到具有输入捕获能力的TIM通道，并用捕获寄存器/可选DMA获得硬件时间戳。

16.1 软件I²C总线：MPU6050和ICM20948共同的底层

④ 拼成int16raw=(high<<8)|low，保留传感器带符号原始数。
⑤ 10 s后去偏置Original-Deviation；Z加速度额外+16384以保留静止1 g。双击按键会把当前Original复制成新Deviation。
⑥ 发布写imu.accel和imu.gyro，供DATA/OLED/停车检测/手柄振动读取。
单位换算：
加速度：a(m/s²)=raw/1671.84，因为±2 g对应±32768；
角速度：ω(rad/s)=raw/3754.9，因为±500 °/s要再乘π/180。
DATA任务做ROS坐标映射：X=传感器Y，Y=-传感器X，Z不变。

例：静止时校准后的Z轴原始值约16384，16384/1671.84≈9.8 m/s²；若陀螺仪Z为3755，则约为1.0 rad/s。串口基础状态帧里传的是原始int16字段，不是IEEE浮点数。

当前IMU算法的能力边界

  • 有：量程/低通寄存器配置、零偏相减、ICM的8点移动平均、坐标轴重映射。
  • 没有：四元数、欧拉角解算、陀螺积分、互补滤波、卡尔曼滤波、磁力计融合和完整静止统计标定。
  • Parking()只使用Y/Z加速度和约8.8的经验差值判断停车/推动车辆，不是严格姿态解算。
  • ICM的ICM20948_Get_Gyroscope()/Get_Accel()声明返回u8，但局部res未赋值便返回；当前调用者忽略返回值，因此不影响主链数值，却不能把它当作可靠错误码。
改量程不能只改寄存器。如果把±2 g改为±4 g，或±500 dps改成±1000 dps，必须同步修改1671.84/3754.9及所有上游阈值。更稳妥的升级是一次burst读取完整14字节/12字节快照，并用数据就绪信号或设备采样率对齐任务。

LX=ch2-1500（前后），LY=ch4-1500（横移），RX=ch3-1500（油门），RY=-(ch1-1500)（旋转）；
各轴先限1000～2000 μs并设±100死区；
Remote_RCvelocity=rc_speed+RX
Vx=LX×Remote_RCvelocity/500/1000 m/s
Vy=-LY×Remote_RCvelocity/500/1000 m/s
Vz=(π/4)×(RY/500)×(Remote_RCvelocity/500) rad/s（Diff）。

CH2大于1600、系统已过启动10 s、掉线计数仍有效且控制模式可用时，条件还要连续累计超过250次TIM1_CC中断才激活RC（这个250按中断进入次数计，不是固定毫秒）；进入RC后的前1 s输出被压为0。任一通道相对上次跳变超过500 μs时，前5次会被拒绝，第6次才接受。Balance任务每10 ms增加掉线计数，而CH3捕获会清零；约110 ms无有效CH3后四路回中/油门归低。

定时器回绕补偿代码使用+9999而不是+10000，会产生1 μs误差，影响很小但概念上应修正。中断里直接更新四个字段，Balance可能看到不属于同一遥控帧的通道组合；安全要求高时应在同步边界发布完整快照。
16.6 游戏手柄：V1.0经典PS2与V1.1/V1.2 USB Host

V1.0经典PS2

PE0=DI、PE1=DO、PE2=CS、PE3=CLK，使用GPIO软件同步协议而非硬件SPI。PSTWO_task优先级4、20 Hz读取9字节报告，再写统一的GamePadInterface。

START激活控制，L1/L2调整速度，摇杆以127为中心并设置死区。连续超过10个周期通信失败后才归中，约0.55 s内可能暂时保留上一条命令，属于需要重视的失联窗口。

V1.1/V1.2 USB手柄

PA11/PA12为USB FS D−/D+。链路是OTG_FS_IRQHandler → 深度16事件队列 → USB Host任务 → HID/非标准HID报告解码 → GamePadInterface。

USB Host任务实际优先级24、栈1024 words，明显高于优先级4的Balance；正常阻塞时没问题，但若USB处理持续就绪，可能挤压100 Hz控制。无报告约0.5 s会清轴，拔出回调会立即恢复默认接口。

两条硬件路径最终都在BALANCE/balance_task.c的PS2_control()中统一转换为Vx/Vy/Vz，再进入同一个电机控制链。也就是说，换手柄协议应主要修改“报告→GamePadInterface”的适配层，不应复制一套新的运动学和PI。

USB的USBH_LL_DriverVBUS()为空实现，程序默认板上硬件持续提供5 V VBUS。排查“USB设备不识别”时，必须测量接口5 V和D+/D−，不能只看软件枚举状态。

17.6 USART2 / D50A：V1.2专用的13字节请求响应

0..2  : AA AA AA
3     : 设备地址
4     : 功能码 D0/D1/D2/D3
5..8  : 数据/参数
9..12 : BB BB BB BB

17.7 OLED：从OLED_GRAM到屏幕像素

OLED不是PB8/PB9的I²C设备。它使用无CS的四线GPIO串行：时钟SCLK、数据SDIN、数据/命令DC和复位RST。老板为PD7/PD6/PD4/PD5组合，新V1.2走PD7、PD4、PE0、PE1组合，准确顺序以HARDWARE/Inc/oled.h当前宏为准。

① 业务写显存OLED_ShowString/Number只修改128×8页的OLED_GRAM。
② 选择页面OLED_ShowTask()根据oled.page把车型、IMU、IP、GY53或诊断字段写入GRAM。
③ 刷新show任务10 Hz调用OLED_Refresh_Gram()，逐页设置地址并发送1024个数据字节。
④ GPIO移位每字节从MSB开始，用SCLK边沿把SDIN送入OLED；无ACK和读回。
⑤ 像素点亮OLED控制器内部显存驱动面板；STM32无法确认屏幕是否真正接收。

切页时代码先OLED_Clear()并立即整屏刷新，然后返回；下一个100 ms周期才绘制新页，所以会产生一次空白刷新。OLED黑屏排错应沿RST/DC/SCLK/SDIN逐层测量：若oled_refresh_enter/exit都增加而无SCLK，查引脚/初始化；有SCLK无显示，查供电、RST/DC极性、版本引脚；只显示但不更新，查show任务和HardFault诊断。

18.4 Drive_Motor()的三层整形

① 输入限幅Vx/Vy/Vz分别限制到±limt_max_speed。Diff默认3.5；这同一数值也限制rad/s，量纲设计并不理想。
② 斜坡平滑每10 ms最多变化smooth_MotorStep=0.02。相当于约2 m/s²的线速度斜率；回充绕过平滑。
③ 逆运动学车体Vx/Vz转换为左右轮目标速度。
④ 轮速再限幅每个Target再限制到最大速度。
⑤ 直线纠偏LineDiffParam以50为中点，对一侧乘1.0～约1.2。
差速逆运动学：
LeftTarget = Vx − Vz × WheelSpacing / 2
RightTarget = Vx + Vz × WheelSpacing / 2

反向正运动学：
Vx = (LeftEncoder + RightEncoder) / 2
Vz = (RightEncoder − LeftEncoder) / WheelSpacing

例：轮距0.329 m，命令Vx=0.500 m/s、Vz=0.400 rad/s，则左轮目标0.500−0.400×0.329/2=0.4342 m/s，右轮目标0.5658 m/s。如果刚从0启动，平滑器不会第一周期跳到这两个值；Vx首先到0.02、Vz到0.02，再逐周期逼近。

直线纠偏函数当前已经有兜底return 1.0f：参数>50只增强左侧，参数<50只增强右侧，50两侧均为1。APP写参数时仍应限制0～100，避免超范围产生过大系数。

18.5 增量PI不是“位置式PID”

e[k] = target[k] − encoder[k]
u[k] = u[k−1] + Kp × (e[k]−e[k−1]) + Ki × e[k]
u[k]最终限制在−16800…+16800。

只有P和I，没有D项。Kp作用于误差变化，Ki对当前误差持续累加；当车轮被卡住时输出会累积到饱和。失能时PI_Controller_Reset()清Bias、LastBias和Output，防止恢复瞬间带着旧积分。

数值例：假设上一输出1200、上一误差0.020，本次左轮目标0.4342、反馈0.4000，Kp=Ki=300：e=0.0342，增量为300×(0.0342−0.020)+300×0.0342=14.52，新输出约1214.52。代码返回int，实际写PWM时发生整数化。

Ki隐含100 Hz采样周期：公式中没有显式dt，所以这里的Ki是“每次采样的离散增益”。如果把Balance从100 Hz改成200 Hz却不重调Ki，单位时间内积分作用大约翻倍。改任务频率必须同时重算编码器速度中的100和PI参数。

ResponseControl()根据电机型号决定是否先把PI输出取反；Set_Pwm()再用符号设置H桥方向GPIO，把绝对值写CCR。TIM8硬件之后自主重复输出PWM，没有“每个PWM周期的电机中断”。诊断变量名中的PWM IRQ指GY53捕获中断，不是TIM8电机PWM中断。

19. 回充、灯光、蜂鸣器、Flash与故障诊断

这些功能看似在控制主链之外，却可能改变命令来源、占用高优先级任务、长时间关中断或让你误判故障。修改前要知道它们何时运行、读写谁以及失败时会影响什么。

19.1 自动回充：CAN握手、导航命令和红外贴桩
① 发现设备发送扩展ID0x12345678，数据01×8。充电板回同ID/特征后置在线。
② 下发贴桩参数20 Hz以标准ID0x105发Dock X/Y/Z和红外刷新时间。速度×1000，大端。
③ 充电板回0x182解析X/Z速度、四路红外、充电位和电流。CAN RX ISR写charger。
④ Balance仲裁有红外用Red_Move；无红外且NavWalk用上位机Up_Move。回充优先于普通控制。
⑤ 失联看门狗在线后约1 s没收到状态就auto_recharge_reset()。重新发现硬件。
0x182载荷含义处理

byte2–3预留/当前Y未使用代码把Y强制设0

19.2 普通LED与RGB灯带：状态优先级和效果算法

普通车型使用低有效三色GPIO（PD14/PD13/PD15），按SysVal.LED_delay闪烁：进入回充黄、充电紫、退出回充回默认红。Diff车型5和Mec车型9会删除普通LED任务，创建优先级2、栈256 words的RGBControl_task。

新板RGB硬件是三路PWM：红PB15/TIM12_CH2、绿PE6/TIM9_CH2、蓝PB14/TIM12_CH1。定时器实际约100 Hz，0～255亮度线性映射到CCR 0～10000。bsp_RGBLight.c还实现了线性渐变、HSV彩虹、sin()呼吸、闪烁和错误码效果。

RGB状态机每秒5次判定，优先级从高到低：
回充/充电 > 低电 > 任一A～F距离<0.5 m > 用户自定义 > 熄灭

GY53在线时A/B/C距离可触发黄色警示，但状态机不检查每路online/新鲜度；GY53掉线后保留的旧近距离可能继续报警。进入控制用途前，应使用同一套“在线+时间戳+迟滞”规则，灯光与电机共享经过验证的障碍物状态，而不是各自比较裸距离。

RGB任务删除死锁风险：RGB_StopEffect()可能直接vTaskDelete()一个正在持有rgb_mutex的效果任务，互斥量将永远不释放。正确模式是发送停止通知，由效果任务自行释放mutex并退出，再由管理者等待句柄清空。另外ChargingCurrent在协议中按mA量级计算，却与0.65f比较，单位明显不一致，应统一成<650 mA或先换算为A。
TIM9还被AKM高级舵机CH1复用时基；修改绿色RGB的TIM9频率会同时改变舵机PWM。改定时器前必须查完整引脚/定时器复用表。
19.3 蜂鸣器：它是开关节拍，不是音频PWM

PD11推挽输出，高电平响、低电平停，要求板上是有源蜂鸣器。没有定时器音调，也不能靠当前接口改变频率。各任务调用Buzzer_AddTask(num,times)向长度10的二维环形数组加入“响几次、每段times×10 ms”。

生产者自检、低电、Flash保存等调用Buzzer_AddTask。
软件队列保存最多10组{num,times}。满时返回0。
show任务驱动Buzzer_task(SHOW_TASK_RATE)在10 Hz被调用。实际时间分辨率是100 ms。
状态机先响real_times，再停real_times，重复num次。不同任务之间固定停约0.5 s。

例如Buzzer_AddTask(1,50)请求响500 ms、停500 ms；由于100 ms调度粒度可以实现。若times=5请求50 ms，小于100 ms最小粒度，代码会拒绝执行。

这个“队列”不是FreeRTOS Queue，多任务同时写head/tail/length没有互斥，存在竞态；建议换成xQueueSend，并增加队列满计数。若要播放不同音高，应另用定时器PWM驱动无源蜂鸣器，不能只缩短show任务周期。
19.4 内部Flash参数：保存的7个word和实时性风险

保存区固定为0x08060000，即STM32F407 512 KiB Flash的Sector 7起点，扇区大小128 KiB。UART4参数命令W置ParamSaveFlag，Balance任务在每个控制周期末检查并执行保存。

word索引保存内容读取后的处理
0Akm_Servo.Min不是0xFFFFFFFF则采用
1Akm_Servo.Mid同上
2Akm_Servo.Max同上
3LineDiffParam当前缺少0～100范围校验
4rc_speed的32位浮点位模式读回后若<0或>10000，恢复500

当前每次保存先进入FreeRTOS临界区，再擦整个Sector 7并写7个word。Flash擦除可能远大于10 ms；临界区内中断停止，而TIM8仍保持最后PWM，车辆可能在控制空窗里继续输出旧动力。

保存设计缺少事务保护：没有magic、版本、长度、CRC、序号、读回验证、双槽或磨损均衡。擦除中掉电会丢全部参数。建议记录格式为{magic,version,length,seq,payload,crc32}，使用两个槽位，启动选择CRC有效且seq最新的一份；只在PE4失能、CCR=0、车辆静止时，由低优先级专用任务写入。
19.5 诊断与Fault：如何从“黑屏”追到真正故障点

USER/system.h的g_system_diag记录启动stage、错误位、任务创建mask、剩余heap、IMU ID、GY53捕获标志/IRQ/心跳、OLED刷新进入/退出、UART超时和Fault寄存器。OLED第5页只显示其中最关键的紧凑字段，完整信息应在Keil Watch查看。

现象先看诊断量判断
OLED从上电起一直不亮stage、IMU ID、任务mask判断卡在板级初始化、IMU识别还是任务创建前。
先亮后冻结show_task_heartbeat、oled_refresh_enter/exitheartbeat停是任务/调度问题；enter增而exit不增是OLED刷新路径卡住。
GY53 P/N不变pwm_irq_count、pwm_task_heartbeatIRQ不增查信号/EXTI；任务不增查创建/调度；二者增再看invalid。
串口一来屏就黑fault_type、CFSR/HFSR/BFAR优先怀疑UART4越界/非法地址，不要先换OLED。
整机无响应且PWM仍有调试器是否暂停、Fault断点普通断点会冻结CPU但不冻结TIM8；致命Fault路径才主动关TIM8。

NMI/HardFault/MemManage/BusFault/UsageFault分别传入fault_type 5/1/2/3/4；SystemDiag_CaptureFault()保存SCB的CFSR、HFSR、MMFAR、BFAR等，再走致命停止：关中断、关闭TIM8 MOE/CCER/CCR/CEN、拉低电机方向脚，有调试器时触发BKPT。

诊断不是掉电日志：g_system_diag当前位于普通BSS，复位启动代码会清零。若Fault后按复位再连接调试器，现场已经丢失。要抓偶发故障，应把最小fault record放到no-init/备份SRAM并带magic+CRC，或在安全可行时写独立Flash日志；仍需避免Fault状态下复杂Flash操作再次失败。

20.3 其他常见修改配方

换IMU或修改IMU采样率
  1. 在system.c增加可靠的ID探测与初始化失败分支，不能把未知设备继续当正常。
  2. 驱动层使用burst读取一个完整样本；返回错误码，不要吞ACK失败。
  3. 明确原始量程和单位换算常量，写入统一imu快照。
  4. 若改IMU_TASK_RATE，同步检查设备内部ODR/DLPF、滤波窗口的实际毫秒数、停车/振动阈值。
  5. 静止标定至少取N点均值并检查方差；标定时检测车辆是否确实静止。
换轮径、减速比或编码器
  1. 确认Keil Target为Diff，并修改CarType/Inc/robot_init.h相关常量和CarType/diff_robot_init.c的对应case。
  2. 复算πD和4×线数×减速比；用手转一圈检查TIM计数绝对值。
  3. 架空低速前进，确认A/B换算后都为正；不对时优先修编码器符号/接线，不要用PI硬顶。
  4. 换机械参数后重新整定Kp/Ki和最大速度，自检阈值也要复核。
改电机PWM频率、通道或方向
  1. 在USER/system.c的MiniBalance_PWM_Init(arr,psc)按TIM8=168 MHz复算频率。
  2. 同步修改HARDWARE/Inc/motor.h通道/引脚宏和FULL_DUTYCYCLE饱和值。
  3. 查新通道是否为高级定时器、是否需要MOE、是否与RGB/舵机/编码器复用冲突。
  4. 方向极性只在Set_Pwm()按电机驱动器真值表修改；加入先零PWM再换向的死区。
  5. 示波器先测空载PWM频率/占空，最后才接驱动和电机。
改UART/CAN协议
  1. 先写协议表：帧头、版本、长度、消息类型、单位、符号、字节序、CRC、超时。
  2. ISR只把字节/帧放队列；解析任务用独立上下文，完成校验后发布结构快照。
  3. 旧协议若要兼容，使用版本字段或新ID，不要用数据长度猜格式。
  4. 发送函数检查队列/邮箱返回值并累计drop/error；接收必须先检查DLC/长度再索引。
  5. 用抓包工具保存一组“正常、截断、错CRC、超长、交错、掉线”测试向量。
增加一个新FreeRTOS任务
  1. 能放入现有周期任务就不要新建；若必须新建，先定义触发频率、最大执行时间和数据所有者。
  2. 栈参数单位是word，乘4才是字节；使用CreateTaskChecked并增加诊断mask。
  3. 优先级必须与阻塞行为一起分析；高优先级任务如果不阻塞，会饿死Balance。
  4. 使用vTaskDelayUntil维持周期，记录heartbeat和stack high-water mark。
  5. 跨ISR/任务数据用Queue、通知、临界区或双缓冲，不把“加volatile”当作完整同步。

20.5 每次修改后的最小闭环验证

  1. 确认当前Keil Target是Diff_Car，map中符号来自你修改的文件，而不是同名旧文件。
  2. 全量Rebuild，记录0 error/0 warning、hex时间和map变化；warning不能在控制项目里被当作无关。
  3. 不接电机或PE4失能，先验证时钟、任务heartbeat、原始输入、单位换算和协议帧。
  4. 用边界值测试：最小/最大/负数/零/掉线/错误CRC/三路同时到达。
  5. 车轮架空，低速验证Target、Encoder、PI、CCR、方向脚和急停；再做地面低速。
  6. 每次只引入一个功能变化，保存“修改前/后Watch或示波器记录”，出现问题才能回到具体层级。
最后的判断原则：显示值不等于原始采集正确，串口能发不等于数据新鲜，online不等于传感器可信，PWM有波形不等于闭环方向正确。每一层都要用它自己的原始量、计数器、单位和超时证据验证。
本手册基于当前工程源码与Diff_Car链接结果整理；硬件接线最终仍应与实物原理图和板卡丝印交叉确认。
