# K7 架构与接口手册

可选 ESP-NOW 一主两从见第 8 节：`ESP32_src/espnow_bridge/` 固件和 `k7_tasks/espnow_bridge` USB/ROS 桥。统一 launch 默认关闭，以 `espnow_role` 和 `vehicle_id` 启用；从车本地 `fleet/leader_state` 使用同一 FleetState。下述主控制链路保持一致。

本手册描述当前工作区；实现与验证状态见 [CLAUDE](../CLAUDE.md)，文档总入口见 [README](../README.md)，可视化见 [架构图](k7-architecture.html)。本手册频率是默认配置/代码周期，不是完整性能基准。

图展示主数据流，不穷举手动转发、授权服务、状态回传和记录器订阅连线；完整接口以本文表格为准。
未完成模块的工作边界、依赖和验收证据见 [开发任务清单](开发任务清单.md)；本手册的接口约束仍以当前源码为准。

## 1. 职责与包

自有活动包共 7 个，不为每种算法复制任务、串口或记录器；外部 `usb_cam` 负责采集。

| 包 | 节点/资源 | 职责与启动条件 |
|---|---|---|
| k7_msgs | 无节点 | 3 个 msg、1 个 srv、2 个 action |
| k7_bringup | serial_bridge | 11/24 字节串口桥、odom 积分、底盘状态；另含统一 launch/config/udev |
| k7_camera | stereo_obstacles | 校正、SGBM、障碍扇区；不默认发布深度图/点云 |
| k7_control | command_guard | 授权、候选超时、前进差速限幅；唯一最终速度出口。底盘禁能/scan/静止/心跳门禁已移除，由上层任务、本车感知与现场急停负责 |
| k7_control | controller_node | APF + Stanley；仅 trajectory/formation 启动 |
| k7_tasks | task_manager | Action 生命周期、互斥、停车确认、遥控、编队参考轨迹 |
| k7_experiment | experiment_recorder | 常驻轻量节点；默认不写盘，可用 record 参数或记录服务启停 CSV、rosbag 和配置快照 |
| k7_description | URDF 等，无默认节点 | 保留模型能力，当前控制不依赖 robot_state_publisher/EKF |
| usb_cam（外部） | usb_cam | USB MJPEG 采集与解码；每车本地运行 |

源码都在 `ROS2_src/K7_ros2/src/`，仅保留以上 7 个自有包。旧算法包、串口实现、双目 splitter/depth 节点、旧 launch/运行脚本及兼容消息已删除。双目保留采集标定图片与离线匹配工具；运行时深度调试复用 `stereo_obstacles.publish_depth`。历史实现查 Git，不在活动源码树保存副本。

## 2. 话题

表中均为相对名称。namespace=car1 时，`odom` 实际为 `/car1/odom`；frame 为 `car1/odom` 和 `car1/base_link`，没有前导斜杠。编队输入是 goal 指定的绝对话题。

| 话题 | 类型 | 发布 -> 订阅 | 默认频率/条件 |
|---|---|---|---|
| camera/image_raw | sensor_msgs/Image | usb_cam -> stereo_obstacles | 10 Hz，3840×1080 并排 RGB |
| camera/camera_info | sensor_msgs/CameraInfo | usb_cam -> 调试客户端 | 驱动输出；不是双目左右标定来源 |
| perception/scan | sensor_msgs/LaserScan | stereo_obstacles -> controller_node、command_guard | 不超过 10 Hz，21 扇区 |
| camera/depth/image_raw | sensor_msgs/Image | stereo_obstacles -> 调试客户端 | publish_depth=true 且有订阅者时 |
| odom | nav_msgs/Odometry | serial_bridge -> task_manager、controller_node、command_guard | 随 20 Hz 上行帧 |
| imu/data_raw | sensor_msgs/Imu | serial_bridge -> 可选消费者 | 20 Hz，原始量；无姿态融合 |
| battery/voltage | std_msgs/Float32 | serial_bridge -> 可选消费者 | 不超过 1 Hz |
| chassis/disabled | std_msgs/Bool | serial_bridge -> command_guard | 20 Hz |
| tf | tf2_msgs/TFMessage | serial_bridge -> 可选消费者 | 20 Hz，odom -> base_link，可关闭 |
| teleop/cmd_vel | geometry_msgs/TwistStamped | 遥控客户端 -> task_manager | manual 才订阅，建议 20 Hz |
| control/reference | k7_msgs/ControlReference | task_manager -> controller_node | 路径任务 5 Hz；编队不超过 10 Hz |
| control/candidate | k7_msgs/MotionCommand | controller_node 或 manual task_manager -> command_guard | 自动 20 Hz；手动随输入 |
| cmd_vel | geometry_msgs/TwistStamped | command_guard -> serial_bridge | 30 Hz，空闲也发送零速 |
| control/status | diagnostic_msgs/DiagnosticArray | command_guard -> task_manager、controller_node | 1 Hz + 状态变化/服务请求 |
| task/status | diagnostic_msgs/DiagnosticArray | task_manager -> command_guard | 1 Hz + 状态变化 |
| fleet/state | k7_msgs/FleetState | task_manager -> 后车 task_manager | 不超过 10 Hz；publish_fleet=true 且对齐确认 |
| control/debug | diagnostic_msgs/DiagnosticArray | controller_node -> 可选 recorder | debug=true，不超过 5 Hz，字段可选 |

感知和 IMU 使用 sensor-data QoS；控制、参考、状态使用深度 1 的默认可靠 QoS。相机订阅使用 sensor-data QoS。过期数据不用于控制。`scan` 是双目推算的前向扇区，不是物理激光雷达；NaN 表示未知并禁止运动，有限有效样本支持的远处空间才可记为 inf。

## 3. 服务与 Action

| 接口 | 类型 | 所属节点 | 语义 |
|---|---|---|---|
| control/select_source | k7_msgs/srv/SelectSource | command_guard | 内部授权：NONE=0/MANUAL=1/AUTO=2；返回 success、permission_id、reason |
| control/hold | std_srvs/srv/SetBool | command_guard | true 锁定停车并撤销权限；false 解除锁定但不恢复旧任务 |
| task/set_manual | std_srvs/srv/SetBool | task_manager | manual profile 的开/关；true 等待授权结果 |
| task/stop | std_srvs/srv/Trigger | task_manager | 请求停车；响应仅表示受理，查看 task/status 确认停止 |
| experiment/record | std_srvs/srv/SetBool | experiment_recorder | 开始/结束一次实验；launch 参数 `record` 控制是否启动后立即记录 |
| task/follow_path | k7_msgs/action/FollowPath | task_manager | trajectory 专用，goal 含 Path、target_speed、position_tolerance、yaw_tolerance |
| task/follow_leader | k7_msgs/action/FollowLeader | task_manager | formation 专用，goal 含 leader_topic、gap、lateral_offset、max_speed；gap 沿前车航向退后，lateral_offset 左正 |

FollowPath 反馈：progress、lateral_error、heading_error、speed、state；FollowLeader 反馈：gap_error、lateral_error、leader_age、state。反馈不超过 2 Hz。两者 result：code（OK=0/CANCELED=1/FAULT=2）、reason；支持标准 ROS Action 取消。服务 stop 中止未取消的 Action，不伪报成功。

任务先申请权限，再输出带本次 UUID 的命令；停止先撤销权限，再等待新鲜里程计连续静止至少 0.3 s，3 s 未确认则 FAULT。一个任务结束前不能并行开始另一个。`task/stop` 可在故障排除后重新执行停车确认，回到 IDLE。hold 不是认证机制，也不是硬件急停：ROS 网络上的节点仍须可信，不能暴露给不可信网络。

## 4. 自定义消息

| 定义 | 字段与目的 |
|---|---|
| MotionCommand.msg | Header、permission_id(UUID)、Twist；阻止上一任务的迟到速度继续控制 |
| ControlReference.msg | Header、permission_id(UUID)、nav_msgs/Path、speed_limit；当前任务的有时效参考 |
| FleetState.msg | Header、session_id(UUID)、float64 x/y/yaw、float32 linear_speed/angular_speed、uint8 state；IDLE/RUNNING/STOPPING/FAULT |
| SelectSource.srv | source -> success、permission_id、reason |

定义目录：`ROS2_src/K7_ros2/src/k7_msgs/{msg,srv,action}/`，只生成表中当前接口。车间不传图片、深度图、完整 odom 协方差或整条路线。

## 5. 任务与扩展

统一用 ROS launch 管理节点和参数，不叠加另一套 shell 状态机。`setup_env.sh` 只安装环境；常用启动命令见 [命令速查](ROS2_命令速查.md)。

| profile | 常驻链路 | 如何开始 |
|---|---|---|
| manual | 相机、感知、guard、serial、tasks、空闲记录器 | 先持续发送零速 TwistStamped，再 task/set_manual=true；授权后持续更新遥控 |
| trajectory | manual 的基础节点 + 一个 controller | FollowPath goal；launch 不硬编码行驶任务 |
| formation | 同 trajectory；按需订阅前车状态 | FollowLeader goal，每车仍用本地双目 |

同一 profile 可顺序发送多个任务；换 profile/算法先停车并确认，再退出 launch、修改配置、重新启动。正常模式算法只接受 `apf_stanley`；传入 mpc 会明确失败，不静默回退。可选 `test_mode:=no_perception` 仅用于 trajectory/formation：不启动相机与双目，控制器仅运行 Stanley，guard 将最终线速度限制为配置的 `test_speed_limit`（代码默认 0.05 m/s，本仓库测试配置为 0.35 m/s）。该模式没有避障或近障保护，须在封闭空旷场地使用并安排现场急停。手动模式不支持该测试模式。

后续接入新算法：实现同一 `ControlReference + odom + scan -> MotionCommand` 边界，复用权限、超时与记录；更新算法选择、参数与测试，仍然只启动一种。MPC 接入时须适配双目输入、限定求解预算和失效输出，再开放选择。规划器可通过 FollowPath Action 提交路径；当前不提供运行中轨迹热替换。GUI 用现有任务/停车/记录接口，不直接控制串口或 cmd_vel。避免为尚未实现的算法预建空包。

## 6. 控制与 STM32

Stanley 使用前方控制点、路径切线航向误差及 `atan2(k*cte, |v_measured| + soft_speed)` 得到等效转向角，再以 `w = v*tan(delta)/control_point` 转为差速车角速度。APF 按障碍降速并叠加转向，最后联合限幅：`v_left=v-w*track/2`、`v_right=v+w*track/2`。限制两轮非负、按比例缩放到最大轮速；行进和转向同时输出。前方控制点可提前修正航向，但不保证有延迟/扰动时横向误差为零就一定航向误差为零。路径终点依据末段位置投影判断，沿 +x 的直线等价于 x 过终点；航向不满足容差时故障停车，不越过终点反复追踪。

固件位置：`STM32F407VET6_src/USER/k7_config.h`、`BALANCE/balance_task.c`、`BALANCE/uartx_callback.c`、`BALANCE/data_task.c`。

- 仅 USART3 合法 11B 帧可更新 ROS 命令；mode/reserved/Vy 必须为零，BCC/帧尾匹配且速度在上限内。
- 100 Hz Balance_task 消费命令、差速联合限幅和轮速 PID；约 300 ms 无合法新命令强制禁能。空闲零速帧维持通信，不等于授权运动。
- 禁用启动自动试车、旧遥控/回充运动覆盖；原低压和急停/禁能检查仍保留，需实车验收。
- 20 Hz 仅发 24B 基础反馈；不发 0xFA/0xFB 红外或算法调试帧，不向其他串口/CAN复制遥测。
- 固定速度上限 0.35 m/s、角速度上限 1.2 rad/s；硬件参数和轮速 PID 仍沿用已有固件，不在 ROS 重写。

## 7. 计算与通信预算

| 链路/任务 | 默认预算 | 注意 |
|---|---|---|
| 串口下行 | 11B × (1000/33) Hz，约 333B/s | 8N1 占线约 3333bit/s，115200 的 2.9% |
| 串口上行 | 24B × 20Hz = 480B/s | 约 4800bit/s，4.2%；全双工分方向计算 |
| 双目 SGBM | 每眼 480×270、64 视差、10Hz、OpenCV 2 线程 | 主算力负担；保留原分辨率采集是为匹配现有标定 |
| 原始 RGB topic | 3840×1080×3×10，约 124MB/s | 本地逻辑数据量，不是 USB MJPEG 码率；避免远端订阅 |
| 控制 | 20Hz，路径最多 512 点 + 21 扇区 | O(N+S)，无优化器；默认单次预算 40ms，超预算不发新候选 |
| 编队 | 10Hz、历史最多 256 点、3cm 间隔 | 单车只订阅前车；FleetState 几何+速度+状态为 33B，另有 Header/UUID/CDR/DDS 开销 |
| 参考路径 | 单车 5Hz、编队至多 10Hz，仅车内 | 最大 512 PoseStamped；并非零拷贝，按实测再优化 |
| 记录 | CSV 5Hz，默认关闭；bag 按选定话题原频率 | 30min/512MB 磁盘余量保护，图像默认不录 |

serial_bridge 以 5ms 周期检查接收，并不以 200Hz 发送遥测。command_guard/candidate/串口分别有独立时效检查；固件最终超时不依赖 ROS 正常退出。

namespace 只分名字，不隔离 DDS 网络。默认未订阅的远端图像没有用户数据接收者，但 DDS 发现仍存在；不要在调试机运行全量录包或订阅所有图像。严格跨机隔离需进一步配置 DDS 分区/路由白名单并实测，当前未实现。没有测量前不承诺具体 CPU 占用或端到端停车距离。

## 8. ESP-NOW 一主两从（可选）

### 8.1 数据流与职责

```text
car1 task_manager 发布 /car1/fleet/state
  -> car1 espnow_bridge 订阅、编码 -> USB/CH340
  -> 主车 ESP32 接收串口帧，ESP-NOW 广播
       ├─ car2 ESP32 接收 -> USB -> car2 espnow_bridge -> /car2/fleet/leader_state
       └─ car3 ESP32 接收 -> USB -> car3 espnow_bridge -> /car3/fleet/leader_state
每辆从车 task_manager 订阅本车 fleet/leader_state
  -> 本车 controller_node -> command_guard -> serial_bridge -> STM32
```

主车只发布自己的状态，两辆从车均跟随 car1。目标点是 `slot = leader − gap·(cos,sin) − lateral_offset·(−sin,cos)`：沿主车航向退 `gap`，向左偏 `lateral_offset`，因此既支持纵向队列，也支持带横向偏移的并排队形。每车仍独立感知和控制。

从车 ESP32 无线只接收，接收到的消息和本板状态经 USB 发给本车 K7；主车 ESP32 也通过 USB 返回本板状态，便于读取 MAC 和检查发送计数。车间链路单向，本车 USB 链路双向。

### 8.3 线协议

USB 与无线沿用同一帧，ESP32 原样转发车辆状态。固定 96 字节，小端，IEEE754 浮点。串口按字节流解析，支持半包、粘包、启动日志和损坏后恢复；无线按完整包处理。

| 偏移 | 类型/长度 | 内容 |
|---|---|---|
| 0 | 2 bytes | ASCII K7，帧头 |
| 2 | uint8 | 协议版本 1 |
| 3 | uint8 | 类型 1=FleetState，2=本板状态 |
| 4 | uint16 | 发送车辆编号 |
| 6 | uint16 | 总长度 96 |
| 8 | uint64 | K7 桥进程 boot_id |
| 16 | uint32 | 消息序号，溢出回绕 |
| 20 | int32 | 原始 ROS 时间戳秒 |
| 24 | uint32 | 原始 ROS 时间戳纳秒 |
| 28 | 16 bytes | 原始 task_manager session UUID |
| 44 | float64 | 共同 fleet 坐标 x，m |
| 52 | float64 | 共同 fleet 坐标 y，m |
| 60 | float64 | yaw，rad，逆时针正 |
| 68 | float32 | 车体前向速度，m/s |
| 72 | float32 | 偏航角速度，rad/s |
| 76 | uint8 | 状态：0 IDLE / 1 RUNNING / 2 STOPPING / 3 FAULT |
| 77 | uint8 | frame_id 的 ASCII 字节数，1..16 |
| 78 | 16 bytes | frame_id，默认 fleet，尾部填零 |
| 94 | uint16 | 前 94 字节 CRC-16/CCITT-FALSE |

类型 2 共用 8 字节头，随后依次为 uptime_ms(uint32)、STA MAC(6 bytes)、role(uint8)、channel(uint8)、usb_rx/radio_tx_done/radio_tx_error/radio_rx/rejected(各 uint32)、保留 54 字节、CRC。完整定义见 C++ 结构体和 Python StatusPacket。

原始消息时间戳和任务会话透传：桥进程 boot_id 用来识别序号归零；session UUID 供编队算法识别主车任务进程重启。接收时重新打时间戳会掩盖源端积压，本实现保留源时间。

### 8.4 刷写三块 ESP32

Arduino IDE 安装 `esp32 by Espressif Systems` **3.3.0**，板型选择 **ESP32 Dev Module**，打开 `ESP32_src/espnow_bridge/espnow_bridge.ino`。同目录的两个头文件一起保留。本例使用自带 WiFi/ESP-NOW/FreeRTOS，无额外 Arduino 库。该示例固定依赖版本，避免发送回调签名随 ESP-IDF 版本变化。

修改 `board_config.h`，分别编译、上传：

| 板子 | IS_LEADER | VEHICLE_ID | LEADER_ID | RADIO_CHANNEL |
|---|---|---|---|---|
| car1 | true | 1 | 1 | 6 |
| car2 | false | 2 | 1 | 6 |
| car3 | false | 3 | 1 | 6 |

主车无需配置 LEADER_MAC。从车要填主车 **ESP32 的 STA MAC**，例如读到 `24:6F:28:01:02:03` 后：

```cpp
constexpr uint8_t LEADER_MAC[6] = {0x24, 0x6F, 0x28, 0x01, 0x02, 0x03};
```

这是示例地址，使用实际地址替换。默认全零 MAC 会使从车拒绝所有无线状态包。主车 MAC 可先刷主车并在 K7 启动桥节点，读取 `fleet/link`；STA MAC 是配置中的目标，开发板 USB 设备序列号是另一回事。

先用 Windows 电脑验证 `电脑 → 主车 USB → ESP-NOW → 从车 USB → 电脑`，再接入 K7。源码入口 `ESP32_src/windows_test/`，详细步骤见[测试工具说明](../ESP32_src/windows_test/README.md)。

### 8.5 K7 安装、串口与启动

各 K7 安装 pyserial、构建工作区：

```bash
sudo apt-get install python3-serial
cd ~/Code/K7_ros2
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select k7_tasks k7_bringup
source install/setup.bash
```

ESP32 的 USB 插 K7 的 USB 主机口，保持 STM32 原来的 USB 连接。用 `ls -l /dev/serial/by-id/` 和 `ls -l /dev/serial/by-path/` 确定 ESP32 串口及稳定路径，写入每车配置 `espnow_bridge.device`。CH340 板可能缺少唯一序列号，此时固定 USB 插口并按 by-path 选择；默认 `/dev/k7_espnow` 只是约定别名。串口权限沿用 dialout/udev；启动桥接后由它独占 ESP32 串口，刷写时先停止桥接程序。

仅检查主车 ESP32 USB、读取 STA MAC 可单独运行：

```bash
ros2 run k7_tasks espnow_bridge --ros-args -r __ns:=/car1 \
  -p role:=leader -p vehicle_id:=1 -p device:=/dev/ttyUSB1
ros2 topic echo /car1/fleet/link --once
```

`sta_mac` 是主车 ESP32 地址；确认后停止单独节点，改用统一 launch。每辆车复制完整 robot.yaml 为自己的配置，在 `espnow_bridge` 字段修改：

```yaml
espnow_bridge:
  device: /dev/k7_espnow  # 替换为本车实际稳定串口路径
  baud: 115200
  leader_id: 1
  channel: 6
  fleet_frame: fleet
  max_age: 0.35
```

各车 `task_manager.fleet_frame` 与桥的 `fleet_frame` 一致。初始同向直线队列的几何示例：

| 车辆 | fleet_x | fleet_y | fleet_yaw | 相对主车的 gap |
|---|---|---|---|---|
| car1 | 0.0 | 0.0 | 0.0 | — |
| car2 | -0.8 | 0.0 | 0.0 | 0.8 |
| car3 | -1.6 | 0.0 | 0.0 | 1.6 |

以上为例子，测量实际起始位姿后设置，确认后在三份配置中设 `task_manager.formation_alignment_confirmed: true`。原 task_manager 在它为 false 时停发本车 fleet 状态。从车初始目标 slot 必须与配置几何一致（`leader − gap − lateral_offset`，默认容差横偏 0.15 m、航向差 0.35 rad），否则 seed 会拒绝并报 `initial pose does not match requested formation offset`。

三台 K7 使用一致的实际时间，桥与跟随算法按源时间判断时效。源状态允许超前最多 50 ms，桥默认接受年龄最多 350 ms，跟随失联门限 500 ms。建议每辆车设置不同 ROS_DOMAIN_ID，车间只走 ESP-NOW，避免 DDS 主车话题与桥重复传递。终端命令均在对应车辆执行：

```bash
# car1
export ROS_DOMAIN_ID=71
ros2 launch k7_bringup robot.launch.py namespace:=car1 profile:=trajectory \
  config:=$HOME/k7/car1.yaml publish_fleet:=true espnow_role:=leader vehicle_id:=1
# car2
export ROS_DOMAIN_ID=72
ros2 launch k7_bringup robot.launch.py namespace:=car2 profile:=formation \
  config:=$HOME/k7/car2.yaml espnow_role:=follower vehicle_id:=2
# car3
export ROS_DOMAIN_ID=73
ros2 launch k7_bringup robot.launch.py namespace:=car3 profile:=formation \
  config:=$HOME/k7/car3.yaml espnow_role:=follower vehicle_id:=3
```

可附加 `test_mode:=no_perception` 做无感知低速测试；其行为和现场限制见第 5 节。从车先确认收到数据（`ros2 topic echo /car2/fleet/leader_state --once`、`/car2/fleet/link --once`），再发跟随任务：

```bash
# car2
ros2 action send_goal /car2/task/follow_leader k7_msgs/action/FollowLeader \
  '{leader_topic: /car2/fleet/leader_state, gap: 0.8, lateral_offset: 0.0, max_speed: 0.10}' --feedback
# car3
ros2 action send_goal /car3/task/follow_leader k7_msgs/action/FollowLeader \
  '{leader_topic: /car3/fleet/leader_state, gap: 1.6, lateral_offset: 0.0, max_speed: 0.10}' --feedback
```

最后给主车发路径任务。启动命令仅启动节点，跟随 Action 和主车路径任务仍由操作端明确发起。

### 8.6 频率、故障与安全边界

- 主车 task_manager 产生不超过 10 Hz 的真实 FleetState；K7 桥和 ESP32 发送调度均限制到最多 10 Hz，调度可能合并最新值，接收频率以实测为准。每帧无线负载 96 字节，设计负载约每秒 960 字节。
- ESP32 接收回调只校验来源、帧长/CRC 并写入单元素队列；普通 loop 负责 USB，避免 Wi-Fi 回调被串口阻塞。主车只转发新 USB 帧，从车只转发新无线帧，不会周期重播缓存状态来伪造心跳。
- K7 校验源车辆、帧坐标、有限数值、时间戳、序号/进程身份；旧包、重复包、乱序包被丢弃。缺包计数既可能来自无线丢失，也可能来自上游最新值合并。
- USB 拔插自动重连；本板状态超时使桥停止接受/发送状态。跟随任务收不到新鲜主车消息时，沿用现有 leader_timeout 停止并撤销权限；故障恢复后的任务按原状态机重新启动。
- 从车本地重建 FleetState 时保留主车 session UUID；主车 task_manager 重启沿用原编队会话检查。整车/里程计重启仍需重新对齐。
- `fleet/link.radio_tx_done` 是主车广播本地发送完成数，无法确认哪辆从车收到。此版本严格无从车无线反馈，主车无法根据链路得知从车在线、障碍或故障。
- 使用未加密广播和主车 MAC 白名单：MAC 白名单用于筛选来源，CRC 用于检测损坏，均非密码学身份认证。需要认证时可升级为两路加密单播并另行确定反馈要求；广播与多播不支持 ESP-NOW 加密。
- 两辆从车都看主车轨迹，car3 无法从通信得知 car2 单独停车；当前靠本车感知/guard 处理前方障碍，全队协同停车需要增加状态回传。

### 8.7 验证范围

本机用真实 C++ 协议头与 Python 编解码器交叉检查 96 字节布局，使用已知 CRC 检查向量、坏帧、半包、粘包、启动文本、序号回绕和重复包测试；Linux PTY 验证实际串口写入，ROS 边界以消息/时钟替身检查原时间戳、会话透传和过期拒绝。Arduino-ESP32 3.3.0 / ESP32 Dev Module 下主车、car2、car3 三份配置实际编译通过（主车 Flash 906063 B / RAM 43612 B；从车 Flash 901035 B / RAM 43396 B）：

```bash
arduino-cli compile --fqbn esp32:esp32:esp32 ESP32_src/espnow_bridge
python3 -m unittest discover -s tests -v
```

Windows 工具覆盖内容错误、重复、乱序、缓存重播、低接收比例和间隔超限检查，并在 Linux 两组真实 PTY 串口上跑通自动识别、发送、暂停、恢复和结果保存。当前本机 54 项回归通过。目标机仍需 ROS Jazzy 构建、ESP32 刷写、三板真实无线收发、时钟与串口路径核对、断链停止、坐标对齐、落地队距和避障验收。协议测试和编译通过分别验证本机逻辑与工具链接口，无线性能以实测为准。
