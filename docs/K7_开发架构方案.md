# K7 智能小车 — ROS2 (Jazzy) 开发架构方案

> 硬件事实以 `CLAUDE.md` 第 13 节为准。

## 一、已确认的决策

| 决策项 | 结论 |
|--------|------|
| ROS2 版本 | **Jazzy**（Ubuntu 24.04 原生支持；参考代码 wheeltec 是 Humble，移植时注意 API 差异） |
| 代码位置 | `ROS2_src/K7_ros2/`（colcon 工作区），wheeltec 留在 `ROS2_src/wheeltec_ros2/` 只读参考 |
| K7↔底盘通信 | **USB 转串口**：K7 USB Host → CH9102F（USB-UART 芯片）→ STM32F407 USART3。K7 端设备名 `/dev/k7_controller`（由 udev 规则从 `/dev/ttyUSB*` 别名绑定），115200 8N1 |
| 手柄 | 2.4G 无线接收器插 K7 USB，内核枚举为 `/dev/input/js0`（摇杆设备文件），用 ROS2 标准包 `joy` + `teleop_twist_joy` 驱动 |
| 摄像头 | LRCP 2MV USB 双目摄像头，单设备输出 3840×1080 左右并排帧，V4L2（Linux 视频采集框架）采集 |
| 开发工作流 | 在 Windows 仓库写码 → `scp -r ROS2_src/K7_ros2/ kickpi@<K7_IP>:~/Code/` → K7 上 `colcon build`；VSCode Remote-SSH 用于板上编译调试 |

## 二、硬件事实摘要

（以下均已在 `CLAUDE.md` 第 13 节与 STM32 固件源码中核实）

- 底盘：WHEELTEC C50X，C50C 主控 V1.0，**STM32F407VET6**（ARM Cortex-M4F, 168MHz），两轮差速
- 轮距 0.329m / 轮径 0.125m；500 线编码器 ×4 倍频（每转产生 2000 个计数脉冲）；减速比 27 或 51 由主板电位器档位决定（固件内部已做换算，ROS 端无需关心）
- 通信协议与 wheeltec **逐字节一致**：下行 11 字节 / 上行 24 字节，int16 大端 ×1000，BCC 校验（逐字节异或，含帧头），上行频率 20Hz
- 上行速度是**整车速度**（固件已做正运动学解算，即从编码器转速换算为机器人整体线速度/角速度），IMU（惯性测量单元，这里指 MPU6050 六轴传感器）上报原始值（仅减去开机零偏），系数与 wheeltec ROS 端一致
- ⚠️ **固件断链不停车**：命令丢失保护被默认关闭 → K7 侧 ROS 层必须实现 cmd_vel 看门狗（下文详述）
- 供电：双电池独立，K7 插电自启，底盘按键开机，两板经 USB 线共地

## 五、节点 / 话题 / TF — 数据流

以下 ASCII 流程图展示了所有 ROS2 节点（node，即独立进程）之间的数据流向。每条箭头上的 `/xxx` 是一个话题（topic，ROS2 的发布-订阅通信通道）。

### 5.1 控制链路

```
/joy ──→ teleop_twist_joy ──────→ /cmd_vel_joy ─┐
teleop_twist_keyboard ──────────→ /cmd_vel_key ─┼─→ twist_mux ──→ /cmd_vel ──→ k7_serial_node
(Phase4) Nav2 ──────────────────→ /cmd_vel_nav ─┘
```

**节点说明：**

- `/joy`：来自手柄驱动节点的原始摇杆/按键数据话题，类型为 `sensor_msgs/Joy`
- `teleop_twist_joy`：ROS2 标准包，将摇杆值转换为速度指令（`/cmd_vel_joy`，类型为 `geometry_msgs/Twist`，含线速度 `linear.x/y/z` 和角速度 `angular.x/y/z`）
- `teleop_twist_keyboard`：同上，从键盘按键转换为速度指令（`/cmd_vel_key`）
- `twist_mux`：ROS2 多路速度指令仲裁节点，同时接收多个 `cmd_vel` 来源，按优先级选择最终执行的速度。配置规则：**joy > keyboard > nav**（手柄永远能抢回控制权）
- `k7_serial_node`：本项目 C++ 节点（`k7_bringup` 包），订阅仲裁后的 `/cmd_vel`，通过串口（`/dev/k7_controller`，115200 8N1）将 11 字节速度帧发给 STM32

### 5.2 底盘传感上行链路

```
k7_serial_node ──→ /odom, /imu/data_raw, /PowerVoltage, /ir_distances
/odom + /imu/data_raw ──→ ekf_node ──→ /odom_combined (+ TF: odom_combined → base_footprint)
/imu/data_raw ──→ madgwick ──→ /imu/data
```

**节点和话题说明：**

- `k7_serial_node`：从串口接收 STM32 的上行帧（主帧 24B + 测距帧 19B + 回充帧 8B），解析后发布底盘状态话题
- `/odom`：里程计（odometry），由编码器速度积分推算，类型 `nav_msgs/Odometry`，包含位置、速度、协方差矩阵，用于机器人短时间内的相对定位
- `/imu/data_raw`：IMU 原始数据，类型 `sensor_msgs/Imu`，含三轴角速度（`angular_velocity`）和三轴线性加速度（`linear_acceleration`），来自底盘 MPU6050
- `/PowerVoltage`：电池电压，类型 `std_msgs/Float32`，单位伏特
- `/ir_distances`：三路红外测距，类型 `k7_msgs/IrDistances`（`front`/`left45`/`right45`，单位米），来自底盘 GY-53 传感器，经 STM32 0xFA 测距帧上行
- `ekf_node`：robot_localization 包中的扩展卡尔曼滤波器（Extended Kalman Filter），**融合** odom 的速度 + IMU 的角速度和加速度，输出更平滑的里程计 `/odom_combined`
- `madgwick`：imu_filter_madgwick 包，对原始 IMU 数据做 Madgwick 姿态解算，输出滤波后的 `/imu/data`（四元数姿态 + 滤波后的角速度和加速度）
- TF（Transform Frame 坐标变换，下详）

### 5.3 视觉链路

```
usb_cam(/dev/k7_camera) ──→ /camera/image_raw(3840×1080)
    ──→ splitter ──→ /camera/left/image_raw + /camera/left/camera_info
                    ──→ /camera/right/image_raw + /camera/right/camera_info
    ──→ stereo_image_proc ──→ /camera/disparity, /camera/points   (需先双目标定)
```

**节点和话题说明：**

- `usb_cam`：ROS2 usb_cam 包，通过 V4L2 从 `/dev/k7_camera`（摄像头 udev 别名）采集原始图像，发布话题 `/camera/image_raw`，为 3840×1080 的左右并排帧
- `splitter`：本项目 k7_camera 包的 Python 节点，将 3840×1080 合并帧裁切为两个 1920×1080 图像，分别发布为左右目话题。`camera_info` 是相机内参文件（焦距、光心、畸变系数），由标定流程生成
- `stereo_image_proc`：ROS2 双目图像处理标准包，根据左右图和标定参数计算视差图（disparity map）和三维点云（point cloud）。在每个像素位置，视差 = 左图该像素水平坐标 − 右图对应点的水平坐标（像素差）；基线约 20mm，有效测距范围大致 0.3~1.5m
- **双目标定**是 stereo_image_proc 的前置条件：需要用棋盘格标定板采集左右摄像头图像，通过 `ros2 run camera_calibration cameracalibrator.py` 计算得到 `camera_info`

### 5.4 TF 坐标变换树

```
map (Phase 4) → odom_combined → base_footprint → base_link → 左轮/右轮/万向轮
                                                  → gyro_link
                                                  → camera_link → camera_left_optical_frame
                                                                 → camera_right_optical_frame
```

**TF 说明：**

TF（Transform Frame）是 ROS2 中描述各坐标系之间相对位姿（位置+姿态）的树状结构。箭头表示"子坐标系在父坐标系中的位置"，例如 `base_footprint` 在 `odom_combined` 坐标系下的位置由 EKF 节点持续发布。

- `map`（Phase 4，地图坐标系）：全局固定参考系，由 SLAM（同步定位与建图）算法维护，定位机器人在世界中的绝对位置
- `odom_combined`（融合里程计坐标系）：EKF 节点发布的平滑定位结果，漂移比纯编码器里程计小，但随时间仍有累积误差
- `base_footprint`（底盘投影坐标系）：机器人在地面的投影中心，是导航控制的实际参考点
- `base_link`：机器人本体坐标系原点（通常取底盘几何中心），`base_footprint` 上方几厘米
- `gyro_link`：IMU 传感器安装位置的坐标系，用于 EKF 和 Madgwick 正确关联角速度测量值
- `camera_link → camera_left/right_optical_frame`：相机光心坐标系链，`optical_frame` 遵循 ROS 约定（z 轴向前即光轴方向，x 轴向右，y 轴向下）

> 沿用 wheeltec 的 TF 命名方案（`odom_combined`、`base_footprint`、`gyro_link`），使 EKF/Madgwick/Nav2 的 wheeltec 参数文件**零修改复用**。

## 七、风险与注意事项

1. **看门狗是第一优先级安全需求**，Phase 2 验收必须包含断链（断开 USB 线或杀死 ROS 节点）停车测试
2. wheeltec 参考代码用 ROS2 Humble，移植到 Jazzy 的已知差异：launch 语法基本兼容；`robot_localization` 和 `imu_filter_madgwick` 参数格式有微调；colcon 编译的 warning 级别更严格
3. 双目基线仅 ~20mm，比一般双目相机窄，有效测距大致 0.3~1.5m，Phase 4 避障需按近距离场景设计
4. 串口节点依赖 wjwwood serial 库：优先 `rosdep` 安装；若无 Jazzy 预编译包则把 vendor（源码嵌入）的 3 个源文件放在 `k7_bringup/third_party/serial/` 中编译
5. K7 的三个 USB 3.0 口分配：摄像头占一个（需要独占带宽），CH9102F 占一个，手柄接收器占一个；**不要经无源 USB Hub 并联摄像头**

## 八、探索性验证（非主线）：仿真 MPC 实车移植

> **定位**：独立于 Phase 1-5 主线的探索性实验，**不作为正式阶段**。目标是把本地仿真工程 `five_version_progressive_r04_with_pid`（MPC 渐进式避障算法）的控制器**原样**搬到 K7，用真实小车闭环验证算法在实机上的可行性。
>
> 为与仿真闭环**逐环节对齐**：不引入 Nav2、不使用深度相机、参考路径直接写死在程序里。控制器算法本体零改动，只替换两端的输入输出。

### 8.1 核心原则：闭环逐环节对齐仿真

仿真闭环（`common/mpc_core.py`）：

```
参考路径(8字形, 常量) + 3路理想射线 {front, left45, right45}
        │
        ▼
 ProgressiveMPC.control(x, y, θ, reference, sensors)  ──→ (v, omega) ──→ step_unicycle 更新 (x, y, θ)
```

实车闭环（**控制器本体零改动**，只换两端 I/O）：

```
参考路径(缩小8字形, 常量写死) + 3路红外距离 {front, left45, right45}
        │
        ▼
 ProgressiveMPC.control(x, y, θ, reference, sensors)  ──→ (v, omega)
                                                          │
                                           /cmd_vel_mpc → twist_mux → k7_serial_node → STM32
                                                          ↑
                                    /odom_combined（EKF 融合里程计）提供真实状态 (x, y, θ)
```

| 仿真输入/输出 | 实车对应 | 改动 |
|--------------|---------|------|
| `step_unicycle` 积分状态 `(x,y,θ)` | `/odom_combined`（EKF 融合里程计） | 状态来源替换，控制器接口不变 |
| 3 路理想射线距离 | **3 路红外传感器**距离 | 传感器替换，接口不变 |
| 参考路径 `generate_eight_path()` | 程序内硬编码缩小 8 字形 | 常量写死，不接任何规划器 |
| `(v, omega)` 直接作用于运动学 | `geometry_msgs/Twist`（`linear.x=v, angular.z=omega`） | 单位/符号约定与仿真一致（正 omega = 左转） |

### 8.2 代码落地情况（k7_mpc 包已搭建，2026-07-26）

从仿真 `common/` 拷贝到 `k7_mpc/k7_mpc/mpc_lib/`：`common_config.py`、`mpc_core.py`、`path_model.py`、`hazard_points.py`、`fuzzy_risk.py`、`fixed_right_bypass.py`、`version_config.py`（**V1 已选定为实车版本**，先跑通再考虑升级 V5）。`environment.py`/`sensors.py` 不拷贝（仿真专用）。

相对仿真源文件的改动（均不动算法逻辑）：

1. `mpc_core.py`：删 `run_simulation()` 及其专用 import（`environment`/`sensors`/`generate_eight_path` 等）
2. `version_config.py`：绝对导入改相对导入（1 行，适配 ament_python 包结构）
3. `path_model.py`：`generate_eight_path` 增加可选传参（不传参时与仿真行为一致）
4. `common_config.py`：按 8.4 实车标定参数（`R_ROBOT`/`SENSOR_MAX_RANGE`/`V_MAX`/`OMEGA_MAX`，注释标出仿真原值）

节点：

1. **红外测距发布**（并入 `k7_bringup` 串口节点，不单独建包）——GY-53 为 PWM 输出（20Hz 方波，距离 mm = 高电平 us ÷ 10），STM32 用 EXTI 双边沿中断 + DWT 周期计数测高电平，距离写入 `s21c_board.rangerA/B/C` 后经**既有 0xFA 19 字节测距帧**上行（未扩 24 字节主帧）；串口节点按三帧状态机解析，发布**单话题 `/ir_distances`（`k7_msgs/IrDistances`，`front`/`left45`/`right45` 单位米）**。引脚 PE5=前方0° / PE7=左前+45° / PE8=右前-45°，对齐仿真的 `SENSOR_ANGLE_OFFSETS = {front: 0°, left45: +45°, right45: -45°}`
2. **MPC 节点**（`k7_mpc/mpc_node.py`，已实现）——订阅 `/odom_combined` + `/ir_distances`，按 `DT_CONTROL=0.07s` 调用 `ProgressiveMPC.control()`，发布 `/cmd_vel_mpc`；路径常量写死在 `mpc_config.py`；首帧里程计时把路径 SE(2) 对齐到当前位姿；每约 5s 日志汇报 SLSQP 求解耗时
3. **fake_ir_publisher**（`k7_mpc` 调试工具）——固件测距帧未就绪前，发布满量程 `/ir_distances` 联调控制链路

twist_mux 仲裁链加入 MPC：`joy > keyboard > mpc`（手柄永远最高优先级，可随时接管）。

### 8.3 明确排除（与主线的差异）

- ❌ **不引入 Nav2** / slam_toolbox / 全局路径规划 —— 参考路径写死在程序里
- ❌ **不使用深度相机** / stereo_image_proc / 点云 —— 感知只用 3 路红外
- ❌ 不做动态路径跟随、不做建图、不做 NPU 检测

### 8.4 实车移植需重新标定的参数

| 仿真值 | 实车注意点 |
|--------|-----------|
| `SENSOR_MAX_RANGE = 3.0` | 红外传感器量程通常远小于 3m（如 0.3~1.2m），须改为实际量程；并核对 `POINT_WARNING_DIST=1.0`、`POINT_SAFE_DIST=0.65` 是否仍在量程内 |

| `PATH_A = 4.0`（8m 跨度） | 缩小到 1.0\~1.5（2\~3m 跨度），常量写死 |
| `V_MAX=0.42 / OMEGA_MAX=1.2` | 先保守限幅（如 0.3 / 0.8），验证稳定后逐步放开 |
| 控制周期 `DT_CONTROL=0.07s` | 先验证 K7 上单步 SLSQP 求解时间 < 70ms，否则降 `BASE_NP/NC` 或换求解器 |
| 起点对准 | 启动前把小车放到路径起点处并对准朝向（或启动时把路径平移到小车当前位姿） |

### 8.5 验证目标

1. K7 上 `colcon build` 编译通过，MPC 单步求解实时性达标（< 70ms）
2. 小车沿硬编码缩小 8 字形跑完整圈，`/odom_combined` 轨迹偏差可接受
3. 路径上放纸箱/人，MPC 自动减速并绕行（右侧避障逻辑生效）
4. 杀掉 MPC 节点，看门狗 500ms 内停车
